# 小额、大额与门店跨日续账

`roll-forward` 只用于把已经封存并成功发布工作簿的小额、大额或门店任务续到紧接的下一会计期间。三种模式必须各自
从自己的前一日工作目录续跑，继续维护三份独立工作簿；财务资料模式不在本功能范围内。

## 前置条件与命令

必须同时保留前一日工作目录、其中的原始聊天快照和它实际发布的旧工作簿。只有旧工作簿、缺少前序工作目录或快照时
不能续账。前序任务必须是 `finished`，全部群已经封存，判定及来源指纹未被改写。

```powershell
python scripts/reconcile.py roll-forward <前一日work> <第二日聊天记录...> `
  --previous-output <旧工作簿.xlsx> `
  --work <全新且不存在的work> `
  --date YYYY-MM-DD
```

新日期必须紧接前一期间。若前序使用自定义 `--from/--to` 会计日边界，续账继承相同窗口长度并从前序结束时刻起算；
不能重叠、跳日或改变时区。模式、群筛选、`Asia/Bangkok`、roster 路径、LINE 本机名和 OCR 开关均从前序任务继承。
新工作目录保存前序 work/run/snapshot、旧工作簿及本期输入的路径与 SHA-256、消息合并统计、会计期间列表和修订血缘；
前序工作目录保持只读，仍可重新生成覆盖前的版本。

## 快照合并与自动切换平台格式

Telegram、WhatsApp、LINE iOS 和 LINE MIUI/Android 继续由统一入口自动发现。前一日与第二日可以使用不同导出格式，
包括 LINE iOS 与 Android 互换；不需要手工选择解析器。

- 平台提供稳定消息 ID 时优先使用；否则以群身份、曼谷时间、发送者、正文及同位媒体事实建立跨快照身份。累计快照重新生成
  显示用的 `S/M` 编号，旧判定按稳定身份迁移，禁止按旧位置硬接。
- 相同消息的丰富版本可以补全缺失媒体。媒体内容前后都有哈希但不一致时停止；已有媒体判定只有在内容 SHA-256
  完全一致时复用，缺失媒体后来补全必须重新查看和分类。
- 同一消息的正文、发送者、时间或回复目标发生冲突时停止。第二日回复前一日票据或消息时保留跨快照引用；找不到
  目标时不能按相邻金额猜测。
- 群 ID、平台或归一化群名冲突时停止，不把同名但身份不同的 Telegram、WhatsApp 或 LINE 群合并。

## 旧工作簿只做发布核对

前一日原始聊天快照和判定始终是事实依据。旧工作簿会读取，用来确认发布内容是否被人工修改，但不能从工作簿反推
聊天事实。纯样式、列宽、字体或颜色变化不算业务修订；单元格业务内容变化默认阻止续账。

经过人工确认的修订使用：

```powershell
python scripts/reconcile.py roll-forward <前一日work> <第二日聊天记录...> `
  --previous-output <旧工作簿.xlsx> --work <全新work> --date YYYY-MM-DD `
  --confirmed-amendments <已确认修订.json>
```

修订文件合同如下：

```json
{
  "contract_version": "group-chat-confirmed-amendments/1.0",
  "previous_output_sha256": "旧工作簿当前文件的 SHA-256",
  "amendments": [
    {
      "group_key": "line:c123",
      "collection": "orders",
      "id": "O001",
      "field": "customer_nickname",
      "value": "已确认昵称",
      "reason": "旧表人工复核后更正",
      "basis": "S00001 的客户原消息",
      "source_messages": ["S00001"]
    }
  ]
}
```

`collection` 只能是当前模式存在的 `orders` 或 `records`；每项必须绑定群、对象 ID、允许修订的字段、明确新值、理由、
依据和前序消息。修订文件必须绑定旧工作簿当前哈希。脚本应用所有修订后会重新生成前序工作簿并逐格比较：只有修订
能够完整且精确解释旧表全部业务单元格变化时才继续；遗漏变化、多余修订或只提供泛化说明都会停止。

## 第二日复核范围和状态

`review next` 从第二日新消息开始，同时返回 `roll_forward_carry` 和所需旧消息上下文。只重读：

- `pending_next_day` 小额/大额订单；
- `pending` 门店记录；
- 门店上一期最后一条正式 closing 余额快照及需继续核对的调拨；
- 前序异常或被新消息直接引用的旧对象及其必要上下文；
- 第二日新订单、新票据及新媒体。

已经完成且未被引用、未发生冲突的旧对象不无差别重读。`open_orders/open_records` 仍只表示当前分页尚未读完；跨日待续
对象已经是完整 `orders/records`，前一日可以封存和出表。

旧版大额 `group-chat-large-daily-decision/1.0` 会在每条 exchange 都有可验证来源资金条目时转换为 2.0 完整订单：
沿用原 ID、从前序聊天补候选客户、补建生命周期，并加迁移提示强制定向复核。没有来源资金条目的旧 exchange 无法
安全还原完整订单，必须停止并用原聊天重建；脚本不会从旧工作簿金额补造资金事实。

小额和大额订单沿用原订单 ID，并维护：

- `completed`：资金履约完成，保存实际完成时间；
- `pending_next_day`：截止期间仍未换完、未回款，或聊天明确次日继续；
- `cancelled`：明确取消/失败，且退款、追回后没有待履行资金。

每次状态变化追加状态、时间、理由和依据消息。已有部分付款和部分回款不代表整单完成；聊天明确仍需继续时显式保持
`pending_next_day`。下一日批次省略生命周期时，脚本只在出现晚于待续状态的新完成或取消证据后自动追加转换。

大额汇总首列是“统计日期”。付款、退款、回款和追回按各自实际消息发生日归属，同一订单可跨多天产生多行；当日未
发生的一侧为 `—`，发生但金额无法确认是“未确认”，真实净额为零才是数值 `0`。`门店开票群` 同时进入大额任务和
独立门店任务，但两套判定不能复制或互相推导。

门店 `pending` 次日完成后沿用记录 ID，票面日期不变，`posting_at` 使用实际入账时间，并追加 `pending → posted`
历史；只有 posted 金额进入实际发生日余额。跨日回复更正仍要求直接引用原票和完整算式。跨店调拨仍按两群各自方向、
同一调拨 ID 和逐币种金额匹配，不自动补造或平账。

## 封存和受保护替换

完成第二日逐页复核后，照常 `seal` 每个未封存群。没有新消息且没有待续对象的群会保持封存；有待续对象、新消息、
引用或新媒体的群必须重新完成复核。通过全部检查后，可先发布到新路径，或原子替换登记的旧工作簿：

```powershell
python scripts/reconcile.py finish <新work> -o <原工作簿.xlsx> --replace-predecessor
```

`--replace-predecessor` 只接受 `run.json` 血缘中登记的旧工作簿绝对路径。脚本在工作目录内生成临时文件，完成全量判定、
媒体哈希、逐格回读和 WPS 兼容检查后，再次核对旧文件哈希并原子替换。路径不符、旧文件在续账后又变化、文件被 WPS
占用或原子替换失败时不覆盖原文件，也不把新任务标为 finished。正常 `finish` 仍拒绝覆盖任何已存在输出。
